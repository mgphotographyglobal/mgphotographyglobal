# Internal Linking Architecture

How MG Photography UAE's blog and service pages link to each other, and how
a future automated publishing workflow (Claude Work, ~1 article/day) plugs
into it without ever editing a React component.

## The model

```
SERVICE / MONEY PAGE  (app/lib/services.ts — 9 real service pages)
        ↑  "Helpful Guides" section (data-driven, service ↔ category match)
   PILLAR ARTICLE      (isPillar: true — one per cluster)
     ↕     ↕            PillarCallout (supporting → pillar) /
                         "Supporting Guides in This Series" (pillar → supporting)
SUPPORTING ARTICLES     (same category/cluster)
     ↕     ↕            "Related Articles" (category → cluster → tags → explicit)
RELATED ARTICLES
```

Every layer is computed at build time from `content/blog/*.md` frontmatter
— nothing here is a hardcoded per-article React array. The only static list
in the whole system is `app/lib/services.ts`, which maps the 9 real service
routes that exist in the repo (this has to be hardcoded once, somewhere —
there is no dynamic service CMS to read it from).

## Frontmatter fields that drive linking

Extending the existing blog schema (`app/lib/blog.ts`), additive and
optional — every existing post keeps working unchanged:

| Field | Default | Purpose |
|---|---|---|
| `category` | — (required, existing) | Also resolves the primary service page, via `serviceForCategory()` matching `categorySlug(category)` against `app/lib/services.ts`. |
| `tags` | `[]` (existing) | Feeds the "shared tags" tier of related-article matching. |
| `relatedSlugs` | `[]` (existing) | Explicit editorial related-post overrides — lowest-priority signal, used as a supplement to topical matching, not a replacement for it. |
| `cluster` | `categorySlug(category)` | Topic cluster key. Only set this when a post's cluster should differ from its category — most posts never need it. |
| `isPillar` | `false` | Marks the one hub/pillar article for a cluster. At most one per cluster. |
| `primaryService` | `serviceForCategory(category)?.href` | Override the service page this article should support, when it differs from the category default. |

## How each direction works

**Service page → blog** (`ServicePageTemplate.tsx`, and a matching block in
the hand-built `app/dubai-newborn-photography/page.tsx`): at render time,
looks up `getPostsByCategory(categorySlug(service.title))`, pillar-first,
capped at 4, and renders a "Helpful `<Service>` Guides" section — only
when at least one published article matches. No article URLs are ever
written into a service page file. Both `ServicePageTemplate` and the
newborn page are Server Components specifically so they can read the blog
content layer directly (see "Why ServicePageTemplate is no longer a client
component" below).

**Blog → service page**: every article's CTA block (`ArticleCTA`, via
`resolveCta()` in `app/lib/blogCta.ts`) always links to its primary service
page — this is the guaranteed baseline link. Authors/automation can add
further natural, in-prose contextual links (as the sample articles do) —
this is never auto-generated by keyword-matching; it is either a human or
the automation workflow deciding, in context, that a link belongs in a
specific sentence.

**Article → pillar**: a supporting article whose cluster has a designated
pillar automatically gets a `PillarCallout` box ("Part of our complete
guide — ..."). A pillar article automatically gets a "Supporting Guides in
This Series" grid of its cluster's other articles.

**Article → article ("Related Articles")**: `getRelatedPosts()` in
`app/lib/blog.ts` ranks candidates in tiers — same category, then same
cluster (if it differs from category), then shared tags, then the post's
own `relatedSlugs` — and stops. **It never pads out to a fixed count with
unrelated "recent" posts** — an article with fewer than 3 genuine matches
simply shows fewer related links (or none, and the section doesn't render
at all). This was found and fixed during implementation: an earlier
version fell back to "just show recent posts," which surfaced a wedding
article underneath a newborn-photography post purely because nothing more
relevant existed yet.

## Thin category/tag pages

Tag pages are only generated (and only appear in the sitemap) once a tag
has **2+ published posts** (`MIN_POSTS_FOR_TAG_PAGE` in `app/lib/blog.ts`).
A tag used by a single article renders as plain, unlinked text on that
article instead of a link to a thin, near-duplicate page. Category pages
have no such threshold — they map 1:1 to the 9 real services, so they're
always a deliberate, valuable grouping even with one article.

## Broken-link validation

`scripts/validate-internal-links.mjs` — reads every `content/blog/*.md`
file and every `app/**/*.tsx` file, extracts internal links, and checks
each one against the site's *actual* routes (derived by walking `app/` for
`page.tsx` files — not a separate hand-maintained list). It flags:

- links to a page/slug that doesn't exist
- links to a draft or future-dated (unpublished) post
- malformed internal hrefs (not root-relative, double slashes)
- missing trailing slash (the site's URL convention)

Findings on **published** content are errors (exit code 1). Findings on
**draft** posts are warnings only, so authors get early feedback without a
draft-in-progress blocking the build. It runs automatically before every
`npm run build` via the `prebuild` npm script, and standalone via
`npm run validate:links`.

## Reciprocal-link discovery (recommendation only, not automatic)

`scripts/suggest-internal-links.mjs` — a read-only CLI, never edits files:

```sh
node scripts/suggest-internal-links.mjs <slug>              # outbound: what should THIS post link to?
node scripts/suggest-internal-links.mjs --reciprocal <slug> # inbound: which older posts could link to THIS post?
```

This is deliberately metadata/recommendation-driven rather than an
automatic keyword-linking engine — it prints suggested targets and natural
anchor phrasing for a human (or the publishing workflow) to place by hand
inside the relevant sentence. Nothing in the repository is ever rewritten
automatically.

## How future Claude Work daily publishing uses this

1. Write `content/blog/<new-slug>.md` with `category`, `tags`, and
   (optionally) `cluster` / `isPillar` / `primaryService` / `relatedSlugs`.
2. Run `node scripts/suggest-internal-links.mjs <new-slug>` (once the file
   exists, even pre-publish) to get a service-page link, a pillar link (if
   applicable), and 2–5 topical article candidates with suggested anchors.
3. Place 2–5 of those as natural in-prose links — never force it if the
   article genuinely doesn't call for that many.
4. Set `status: "published"`. The CTA, service-page "Helpful Guides"
   section, pillar/supporting relationship, and "Related Articles" all
   update automatically on the next build — zero component edits.
5. Run `node scripts/suggest-internal-links.mjs --reciprocal <new-slug>` to
   find older posts worth updating with a link back to the new one, and
   add those links by hand where they fit.
6. `npm run build` (or its `prebuild` step) will fail the build if any
   link introduced in steps 2–5 is broken, malformed, or points at a draft.
